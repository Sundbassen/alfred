# Project patterns: architecture and what goes where

Alfred's backend (`backend/`, Go module `github.com/sundbassen/alfred`) has three layers. Follow this layout for all new code, and when planning changes.

## Layers and the dependency rule

```
cmd/       may import anything
skills/    may import internal/            (the domain layer: what Alfred can do)
internal/  may import only internal/       (plus the standard library and third-party modules)
```

- Nothing imports `cmd/`. Go's `internal` rule already stops anything outside `cmd/` from importing `cmd/internal/...`.
- `make layers` (run in CI) fails if `internal/` imports `skills/` or `cmd/`, or `skills/` imports `cmd/`.
- **Within a skill:** `<skill>service` and `<skill>store` both import the skill (its domain types and interfaces), never each other, and the skill imports neither. A provider that needs persistence takes the skill's `Store` interface in its constructor; wiring passes `<skill>store.New(db)` to it.

## What goes where

| Path (under `backend/`) | Holds |
|---|---|
| `cmd/<binary>/` | `main` only: flags, logging, lifecycle. Binaries: `alfred` (all-in-one: its own mic and speaker), `hub` (for satellites, #54), `replaywav`, `reviewrecordings`, `wakestats`, `micdebug` |
| `cmd/internal/wiring/` | The composition root. `skills.go` constructs the providers (external implementations) and calls every skill's `Register`. It's the one place to see which providers Alfred uses |
| `skills/<skill>/` | One skill: its intent types, its handlers, the interfaces its handlers need, and `Register(r *assistant.Router, deps...)` registering all of its intents. There is no `skills` package, only one package per skill |
| `skills/<skill>/<skill>service/` | Providers implementing that skill's interfaces, one file per provider (e.g. `musicservice/spotify.go` with `NewSpotify(...) *Spotify`). Constructors return concrete types. The skill never imports this package; this package may import the skill (for its types and interfaces) and `internal/`. It depends on the skill's `Store` interface, never on `<skill>store` |
| `skills/<skill>/<skill>store/` | Persistence for that skill: `<skill>store.go` implements the skill's `Store` interface. It only calls the generated queries (`internal/store/storedb`) and converts their rows to and from the skill's domain types. Kept separate from `<skill>service` (external providers): it imports only the skill and `internal/store/storedb`, and nothing but wiring imports it |
| `internal/assistant/` | The intent contract and router: `Intent`, `Handle[I]`, `Router`, `Response`, `Spec`, `SpokenError`, `SpokenText` |
| `internal/assistant/match/` | The phrase-template recognizer (the first tier) |
| `internal/assistant/llm/` | The model-agnostic language-model recognizer: prompt and JSON schema from the intents, validation of the answer. Models plug in through its `Model` interface. It also holds the model contract every model user shares (`Request`, `Result`, `Token`, `Schema`, `TextConfidence`). Further recognizers (e.g. the Claude fallback) go alongside and produce the same `assistant.Recognition` |
| `internal/llm/<model>/` | Language model implementations of `llm.Model` (e.g. `ministral`), plus `internal/llm/llamaserver` (runs llama.cpp's server as a child process) |
| `internal/app/` | Wires the voice framework into a listener, plus `Assistant` (recognize → dispatch). It never imports skills |
| `internal/voice/` | The voice framework: `listener`, `wakeword`, `stt`, `vad` (+ `silero`), `mic`, `tts`, `sound` (the chime), `recorder`. Its contracts are in `voice.go` |
| `internal/hub/` | The hub's satellite side: a session per satellite (over `internal/esphome`), the voice pipeline per request (endpointing with `listener.Recorder`, transcription, `app.Assistant`, text-to-speech), a media server for reply audio, and announcements (it is the clock's `Announcer` in `cmd/hub`) |
| `internal/esphome/` | Client for ESPHome's native API, how the hub talks to satellites (#54): framing (plaintext and Noise), `Dial`/`Keep` (reconnect), `Accept` (the device side, for tests), `esphomepb` (generated by `make proto` from the vendored `proto/esphome`), `esphometest` (a fake device) |
| `internal/store/` | Alfred's local SQLite database (`modernc.org/sqlite`): `Open` (pragmas in the connection string, mode 0600), the one shared schema in `migrations/NNNN_name.sql` (numbered, up-only, every table `STRICT`), the queries in `queries/` (one file per table or area), and `storedb`, generated from them by sqlc. Cloud-owned user data does not go here (#39) |
| `internal/spoken/` | Spoken language for skills: parsing times, durations, days and numbers as people say them (`ParseWhen`, `ParseDay`, `Number`) and saying them back (`FormatDuration`, `FormatClock`, `FormatRemaining`, `JoinAnd`, `JoinOr`, `SecondPerson`) |
| `internal/platform/` | Shared helpers: `fault` (error categories, see `go-errors.md`), `pcm`, `wav`, `onnxrt`, `logging`, `wakeclip` |
| `internal/<client>/` | Infrastructure shared by several skills (e.g. `internal/homeassistant`, an API client used by lights and climate). Each skill's service package adapts it to that skill's interface |

## Recipes

**Add a skill:**
1. Create `skills/<skill>/<skill>.go` with:
   - intent types: concrete structs with a value-receiver `IntentName()`; parameters are fields;
   - handlers: `func(ctx, I) (assistant.Response, error)`;
   - the interfaces the handlers need;
   - `Register(r *assistant.Router, deps...)`, which calls `assistant.Handle` for each intent with a `Spec` (description and example phrases), with `Help` set on the intents that represent the skill (usually one) so "what can you do" mentions it (a short phrase without commas, e.g. "set timers and reminders").
2. Add one line to `cmd/internal/wiring/skills.go`.

**Add a provider:**
1. Add `skills/<skill>/<skill>service/<provider>.go`, implementing the skill's interface.
2. Construct it in `cmd/internal/wiring/skills.go` and pass it to the skill's `Register`.

**Switch or add an intent model:**
1. Add `internal/llm/<model>/` implementing `llm.Model` (usually a thin layer over `llamaserver`).
2. Construct it in `cmd/internal/wiring/assistant.go` instead of, or as a tier after, the current one.

Recognition, the router and the skills don't change.

**Add a table:**
1. Add the next migration, `internal/store/migrations/NNNN_name.sql`, ending the `CREATE TABLE` with `STRICT`. Store times and durations as `INTEGER` milliseconds.
2. Write its queries in `internal/store/queries/<table>.sql`.
3. Run `make sqlc` and commit the regenerated `internal/store/storedb`; CI runs `make sqlc-diff`.
4. In `skills/<skill>/<skill>store/<skill>store.go`, call the generated queries and convert between their rows and the skill's domain types.

**Give a skill the language model** (e.g. `skills/answer`):
1. The skill declares the interface it needs, shaped like `llm.Model` (`Generate(ctx, llm.Request) (llm.Result, error)`), and uses the `llm` types; no `<skill>service` adapter is needed.
2. Wiring passes `Deps.Model` (`wiring.StartModel`, shared with the intent tier; nil without a model, then the skill is left out) and registers a warm-up with `Model.OnReady`.
3. To take transcripts nothing else recognizes, `wiring.NewAssistant` sets `app.Assistant.SetFallback`.

**Add shared infrastructure:**
1. Add a client package in `internal/<client>/`.
2. Adapt it per skill in each skill's `<skill>service` package.

**Coordinate skills** (e.g. `skills/stop`: "stop" stops a ringing timer before the music):
1. The coordinating skill defines the interface it needs (`stop.Stopper`, plus a func adapter).
2. Wiring passes the other skills' objects (`*clock.Timers`) or adapters over their providers, in priority order. Skills never import each other.

## Configuration

- **Providers are configured through the environment:** `ALFRED_<PROVIDER>_<SETTING>`, read in one place, `wiring.ConfigFromEnv()` in `cmd/internal/wiring`, into a `Config` struct of provider configs (e.g. `musicservice.SpotifyConfig`).
- **A skill whose provider isn't configured, or isn't logged in, is left out with a log line** instead of failing startup. Alfred keeps working without it.
- **Secrets and tokens live outside the repo** (e.g. `~/.config/alfred/`), written with mode 0600.

## Conventions

- **Handlers are transport-agnostic:** they take `(ctx, concrete intent)` and return `(Response, error)`, and never see voice or HTTP types. A future HTTP API (`POST /intents/{name}`) dispatches to the same handlers.
- **Follow-up questions:** a handler that needs more ("Which one?", "Should I create it?") returns `Response{Text, Ask: &assistant.Question{Intent, Slot}}` with the intent partly filled: the answer fills `Slot` (or, without a slot, yes dispatches the intent as is). `app.Assistant` keeps the question (one pending question per assistant, i.e. per conversation; the question isn't part of the serialized response) and the front end listens for the answer without the wake word. Data the answer must not lose (e.g. which timers were listed) goes in a non-slot field of the asked intent. Prefer this over a `SpokenError` that makes the user start over.
- **Interfaces live with their consumer** (the skill), not with the implementation. Don't define an interface before something uses it.
- **Dependencies are passed explicitly** through constructors and `Register`: no globals, no `init()` registration, no DI framework.
- **Errors** follow `.claude/rules/go-errors.md`: tozd errors, with generic categories in `internal/platform/fault`.
